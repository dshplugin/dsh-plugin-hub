**v1.4.8 — installs stop failing for the wrong reason**

DSH Plugin Hub is the community plugin marketplace for DeepSeek Harness. This release is about trust in the install result: packages that declare their entry correctly are no longer rejected, one registry hiccup no longer decides which channel a repository uses for the rest of the session, and two crash paths inside the host process are closed.

**Website**: [dsh-plugin.org](https://dsh-plugin.org)

**What's New**

- **Plugins that declare their entry through `exports` install again** — A package whose entry file is declared as an `exports` string target (for example `"./lib/index.js"`) was looked up as `package/./lib/index.js` inside the git tarball, which tar never matches. Every such plugin was blocked with `400 entry file missing` before it could install. The leading `./` is now stripped.
- **Dual-condition `exports` no longer turns a successful install into a failure** — When a package declares its entry as an object (`{ "import": ..., "require": ... }`), only the `default` key used to be understood; anything else fell back to `index.js`, so the post-install verification could report failure for a package that had installed fine. Entry resolution now lives in one shared helper used by both the pre-install check and the post-install verification, and it accepts the first string among `default`, `import` and `require` — then `main`, then `index.js`, as before.
- **A transient registry failure no longer pins a repo to the git channel** — The npm reverse lookup treated every failure mode — timeout, DNS error, non-200, invalid JSON — as a confirmed "no npm package" and cached it for the lifetime of the process. One registry outage during the first install of a repository therefore sent every later install of that repository down the git path and dropped the repo-to-package mapping used by the installed-state check, until the host restarted. Only confirmed outcomes are cached now: a matched name, or an empty result from a `200` response. Unconfirmed attempts are retried on the next install.
- **An install task that throws no longer takes the host process down** — The queue pump discarded a throw from the mutation (reachable through the build-recovery path's `writeFileSync` on a read-only or full disk) as an unhandled rejection, which is process-fatal on Node 15+, while the queue kept running. The throw is caught and the task is reported as failed, like any other install failure.
- **Choosing a log directory can no longer crash the host** — On Linux without `zenity`, the file picker's `spawn` emits both `error` and `close`, and both handlers answered the same HTTP request; the second call ran `writeHead` on an already-ended response and threw `ERR_HTTP_HEADERS_SENT` as an uncaught exception. Only the first event answers now, and the `500` from `error` is the one returned.
- **Package metadata now reads `10000+`** — The catalog passed 10,900 verified entries, so the hardcoded "9000+" copy in the published metadata, both READMEs and the site now reads `10000+`, identical in Chinese and English and without a thousands separator.

**Installation**

Option 1 · via npm (recommended):

```bash
dsh plugin --profile web add dsh-plugin
```

Option 2 · via the official GitHub repository:

```bash
dsh plugin --profile web add git+https://github.com/dshplugin/dsh-plugin-hub.git
```
